# VeighNa 项目开发规则

## 1. 项目概述

VeighNa是一套基于Python的开源量化交易系统开发框架，旨在为专业量化交易员提供一站式多因子机器学习策略开发、投研和实盘交易解决方案。

## 2. 开发理念

- **为交易员而生**：优先满足机构专业交易员的使用习惯
- **对新用户友好**：提供简洁易用的API和完善的文档
- **尊重他人，慎重言行**：保持礼貌文明的交流方式
- **追求卓越**：不断优化代码质量和性能
- **注重安全性**：保障交易系统的稳定性和安全性

## 3. 代码规范

### 3.1 语言版本

- 使用Python 3.10+开发
- 支持Python 3.10, 3.11, 3.12, 3.13
- 所有代码必须兼容指定的Python版本

### 3.2 代码风格

- 使用ruff进行代码风格检查，确保无error和warning
- 运行命令：`ruff check .`
- 配置文件：`pyproject.toml`中的`[tool.ruff]`部分

### 3.3 类型注解

- 使用mypy进行静态类型检查
- 运行命令：`mypy vnpy`
- 配置文件：`pyproject.toml`中的`[tool.mypy]`部分
- 所有公共函数和方法必须添加类型注解
- 尽可能为内部函数和方法添加类型注解

### 3.4 代码结构

- 每个模块应保持职责单一
- 避免过大的文件（建议单个文件不超过500行）
- 合理使用类和函数组织代码
- 遵循Python的PEP 8命名规范
  - 类名：驼峰命名法（如`MainEngine`）
  - 函数名和变量名：下划线命名法（如`add_gateway`）
  - 常量：全大写加下划线（如`MAX_ORDER_SIZE`）

### 3.5 文档注释

- 为所有公共类、函数和方法添加文档字符串
- 使用Google风格的文档字符串格式
- 文档应包含：功能描述、参数说明、返回值说明、异常说明（如有）
- 示例：
  ```python
  def add_gateway(self, gateway_class: type) -> None:
      """添加交易接口。
      
      Args:
          gateway_class: 交易接口类
      """
      pass
  ```

## 4. 开发流程

### 4.1 分支管理

- **master分支**：稳定版本分支，仅用于发布正式版本
- **dev分支**：开发分支，所有新功能和bug修复都应基于此分支
- **feature分支**：新功能开发分支，命名格式：`feature/feature_name`
- **bugfix分支**：bug修复分支，命名格式：`bugfix/bug_description`
- **hotfix分支**：紧急修复分支，命名格式：`hotfix/fix_description`

### 4.2 开发步骤

1. **创建Issue**：对于较大的改动（如新功能、大型重构等），建议先创建Issue讨论
2. **Fork仓库**：从主仓库Fork到自己的GitHub账号
3. **克隆仓库**：`git clone https://github.com/$userid/vnpy.git`
4. **创建分支**：从dev分支创建自己的功能分支
5. **开发代码**：遵循代码规范开发功能或修复bug
6. **测试代码**：确保代码通过所有测试
7. **提交代码**：
   - 提交信息应清晰描述改动内容
   - 提交信息格式：`[模块名] 简洁的改动描述`
   - 示例：`[trader] 添加新的交易事件类型`
8. **推送分支**：将本地分支推送到自己的Fork仓库
9. **创建Pull Request**：从自己的功能分支向主仓库的dev分支创建PR
10. **代码审查**：等待项目维护者审查代码
11. **合并代码**：审查通过后，代码将被合并到dev分支

### 4.3 Pull Request规范

- PR标题应清晰描述改动内容
- PR描述应包含：
  - 改动的目的和背景
  - 具体的改动内容
  - 相关的Issue编号（如有）
  - 测试情况
- PR应保持小而专注，每个PR只解决一个问题或添加一个功能
- 确保PR通过所有CI检查

## 5. 测试规范

### 5.1 测试类型

- **单元测试**：测试单个函数或类的功能
- **集成测试**：测试多个模块之间的交互
- **回归测试**：确保修复bug后不会引入新的问题
- **性能测试**：测试代码的性能表现

### 5.2 测试要求

- 所有新功能必须添加相应的测试用例
- 所有bug修复必须添加回归测试用例
- 测试覆盖率应不低于80%
- 测试代码应与生产代码分离，存放在`tests`目录下

### 5.3 测试运行

- 运行所有测试：`python -m pytest tests/`
- 运行特定测试：`python -m pytest tests/test_module.py`

## 6. 文档规范

### 6.1 文档类型

- **API文档**：自动生成的API参考文档
- **用户文档**：存放于`docs`目录下，包括安装指南、使用教程、API参考等
- **示例代码**：存放于`examples`目录下，展示各种功能的使用方法
- **README文件**：项目的基本介绍和快速开始指南

### 6.2 文档要求

- 文档应保持最新，与代码同步更新
- 文档应清晰、简洁、易于理解
- 示例代码应可运行，并且包含必要的注释
- 文档应使用Markdown格式编写

## 7. 版本管理

### 7.1 版本号格式

使用语义化版本号格式：`MAJOR.MINOR.PATCH`

- **MAJOR**：重大版本更新，可能包含不兼容的API变更
- **MINOR**：新增功能，向后兼容
- **PATCH**：bug修复，向后兼容

### 7.2 发布流程

1. 更新版本号：修改`vnpy/__init__.py`中的`__version__`变量
2. 更新CHANGELOG.md：记录版本变更内容
3. 运行测试：确保所有测试通过
4. 构建发布包：`python -m build`
5. 发布到PyPI：`twine upload dist/*`
6. 创建GitHub Release：包含发布说明和二进制文件

## 8. 依赖管理

- 所有依赖应在`pyproject.toml`中声明
- 依赖应指定版本范围，避免使用固定版本（除非有特殊原因）
- 新增依赖应经过充分评估，确保其稳定性和安全性
- 定期更新依赖，修复安全漏洞

## 9. 安全规范

- 不得在代码中硬编码敏感信息（如API密钥、密码等）
- 所有网络请求应使用HTTPS协议
- 输入数据应进行验证，防止注入攻击
- 定期进行安全审计，修复潜在的安全漏洞
- 遵循最小权限原则，只授予必要的权限

- 官方论坛：https://www.vnpy.com/forum

### 10.2 行为准则

- 遵守项目的行为准则（CODE_OF_CONDUCT.md）
- 尊重他人，保持礼貌和专业

## 11. 代码审查

### 11.1 审查内容

- 代码风格和质量
- 类型注解的正确性
- 功能的完整性和正确性
- 测试覆盖率
- 文档的完整性和准确性
- 性能和安全性

### 11.2 审查流程

1. PR创建后，自动触发CI检查
2. 项目维护者或其他贡献者进行代码审查
3. 审查者可以提出修改意见
4. 开发者根据意见进行修改
5. 审查通过后，PR被合并

### 11.3 审查反馈

- 反馈应具体、明确，指出问题所在
- 提供建设性的改进建议
- 对优秀的代码给予肯定和鼓励
- 保持礼貌和尊重
